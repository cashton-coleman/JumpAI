# JumpAI

When installed and enabled, using a matching available Jump AI capability is mandatory before recreating reusable coding mechanics. Use the catalog for source inspection, guarded edits, data preparation, checks, and multi-step development workflows. Ordinary tools remain appropriate for trivial commands, work with no suitable capability, a blocked installation, or an explicit user exception.

The bundled [working standards](AGENTS.override.md) cover code hygiene, focused tests, concise communication, and mandatory use across agents. The installer embeds them in host startup guidance; use that supplied context without rereading this file. Read the bundled standards once only when they are absent from the current context. Pass them with the applicable command or prepared handoff to authorized child agents that lack inherited guidance.

For installation, upgrades, removal, or missing cross-chat discovery, use the bundled [installation lifecycle](references/installation.md). Install skill discovery and host startup guidance together; copying the skill folder alone does not install startup instructions. For delegated unittest diagnosis, use `--library LIBRARY_JSON --workspace CHILD_WORKSPACE handoff --prepare --read-only --source RELATIVE_FILE --tests '["unittest_id"]'`. This runs initial checks and gathers checkpoint evidence once. Pass `child_assignment` unchanged to one fresh child. The child must return a repair decision and brief reason without tools, reads, repeated checks, or further delegation. The parent uses a blocking wait (60000 ms where supported), reviews the decision, and appends `--decision JSON` to `resume_command`; final checks and reporting are built in. If preparation completes successfully, no child is needed. A specific missing fact is returned as `needs_evidence`; retrieve only that context instead of guessing. Do not reread known skills/contracts or poll in short intervals. These are required execution rules for matching work, except an explicit user instruction such as an ordinary-tool comparison control. Omitting `--prepare` retains the command-card interface for other callers.

Invoke `python3 <this-skill-directory>/scripts/jumpai.py ...` from the task workspace. The launcher locates the JumpAI checkout through its resolved path, so it also works through a skill symlink. An installed `jumpai` CLI is equivalent. Prefer the installed startup command with `--library /absolute/catalog/library.json --workspace /absolute/task`: it reads published definitions and stores mutable caches, runs, and sessions under the task's `.jumpai/runtime`. This needs no write to the shared catalog. Use the same workspace for a child's diagnosis and the parent's resume. Explicit `--home <writable-catalog>` and `JUMPAI_HOME` remain available for catalog administration; `publish-library` or reinstall publishes global updates.

- For matching Python unittest repair tasks, use `repo.regression-triage@1.4.0` with `{root, source_path, tests}` and `--resumable`; it runs tests and gathers evidence before pausing for a repair. A read-only source assignment may start this workflow, but must stop at the checkpoint. For checks only, use `triage.run-checks@1.0.1` with `{root, tests}`. These installed contracts can be used directly, without discovery.
- If the pinned capability and its contract are already known, use `run --target name@version --input '<json>'` directly.
- For requested per-reply usage reporting, run `usage --footer` once and append that line to the final response. It reads the current local Codex thread through `CODEX_THREAD_ID`; use `--session /absolute/rollout.jsonl` when its path is already known. Missing telemetry is unavailable, never an estimate. See [usage details](../../DEVELOPER_GUIDE.md#usage-footers) for accounting and supported evidence.
- Installation probes native C++17 compilation and execution, then persists the preferred runtime in SQLite. The runner uses C++ for `runtime=cpp` programs when enabled, otherwise their declared `python_fallback`; Python programs remain supported. Use `settings` to inspect the detected compiler and preference when authoring native programs. See [authoring](references/authoring.md) for the manifest contract and [installation](references/installation.md) to change the preference.
- Native binaries are cached per workspace and rebuilt in the background when bundled source or toolchain identity/dependencies change. Compiler identification is cached; macOS/BSD file-event watches avoid repeated header scans. Unsupported hosts retain full dependency checks. While dependency validation or building is pending, use the declared Python fallback; native-only programs return a pending error so other work can continue. Do not poll repeatedly. The run's `native_build` field reports build state and failures. Explicit `verify` waits for the native build to ensure it tests C++.
- `reports.combine@1.1.0` assembles `{inventory, links, tests}` into a repository report using cached C++ or its Python fallback. The runner validates and serializes the JSON contract; the native program forwards its validated contents without changing numbers or Unicode.
- If the task context already supplies a saved recipe command for the intended work, execute it directly: `jump <name> --cwd <workspace>`. No skill, search, resolve, or contract read is needed for that known invocation. `--with '<json object>'` replaces top-level arguments for this run only; use it only when those arguments are known.
- To prepare future direct invocations, add `--save-recipe <name>` to a successful validated `run`. It explicitly persists the input arguments and returns a compact recipe card with a shell-quoted command. Retain that card in the host's task context or workspace instructions, with its purpose and applicability; this is what lets a fresh agent skip setup reads. Avoid saving secrets as arguments; prefer file paths. A missing/stale recipe returns exit 3 without executing; recover by selecting a target and saving a new successful invocation.
- For a repeated request with known arguments, use `run --query '<stable request phrase>' --input '<json>'`. A valid SQLite resolution executes directly; a miss returns candidates and exit code 3 without running anything.
- For a conditional workflow with decision checkpoints, use its recipe command with `--resumable` (or `run --target ... --input ... --resumable`). It runs deterministic steps internally and returns a compact receipt. On `needs_decision`, use the provided evidence directly when complete relevant definitions and failure facts explain the decision. Respect explicit omissions and read referenced evidence or source when missing context matters; do not reread an identical complete definition merely to confirm it. Then `resume <session_id> --step <decision.step> --decision '<json>' --cwd <original-workspace>`. Supply judgment matching the returned schema; do not reconstruct completed steps. `completed` includes a compact `summary`; request `result <session_id>` or `result <session_id> --step <name>` only if more detail is necessary. All session commands require the original `--cwd` and catalog.
- Resume only explicit decision checkpoints. Invalid or stale decisions are rejected; failed/running sessions cannot be blindly resumed because earlier steps may have side effects. `status <session_id>` inspects progress without executing. Add `--save-recipe <name>` to the completing `resume`, or to a resumable `run` that completes immediately, to save original arguments for a new run; decisions and outputs are not part of the recipe. If the start pauses, no recipe is saved; pass the flag again on the completing resume.
- When the contract is needed, use `resolve '<phrase>'`. A cache hit includes its pinned contract. On a miss, inspect a suitable candidate with `inspect name@version`; search results are suggestions, not automatic selections.
- After selecting a validated program, use `run --target name@version --input '<json>' --remember '<phrase>'`. Only successful execution creates the binding. Keep the request phrase stable across repeats. For multiple applicability contexts in one workspace, pass a consistent `--context` key; `run` scopes caching to `--cwd`, while `resolve` and `remember` use `--scope`.
- If nothing fits, complete the task and capture useful repeatable mechanics as a program. Read [the authoring reference](references/authoring.md) when adding programs or compositions. Register, verify representative cases, and only then remember the capability.

Resolution bindings cache the choice of program. Opt-in recipes additionally store arguments, scope, and context. Neither stores execution results. Reuse still executes against current inputs. Catalog mutations invalidate both kinds of binding; repeat selection when needed. Execution errors require diagnosis, not blind retries, especially when a program can modify files or external state.

Opt-in resumable sessions separately persist inputs, decisions, and intermediate results in local SQLite to continue the same run. Keep large or sensitive evidence in appropriate files and pass references; avoid retaining secrets in session data. A new recipe invocation starts a new session and reads current inputs.

Programs run with the caller's permissions and environment. Registration and passing fixtures do not grant additional authority or establish a sandbox. Inspect unfamiliar code before executing it. Prefer compact outputs and file paths for larger artifacts; intermediate workflow data stays inside the runner.
